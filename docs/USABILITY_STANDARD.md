# Universal Usability Requirements for Mobile Stateful Products

Версия: 1.5  
Статус: живой адаптивный каркас для проектирования и развития продукта  
Назначение: сохранить проверенные usability-решения в универсальной форме

## 1. Как использовать документ

Этот файл задаёт требования к продуктам, в которых пользователь регулярно:

- создаёт и изменяет данные;
- проходит многошаговые сценарии;
- взаимодействует с приложением на телефоне;
- получает предложения или автоматически обработанные результаты;
- возвращается к прогрессу в разные дни;
- может ошибиться и должен иметь возможность исправить результат.

Документ не описывает конкретного пользователя, расписание, предметную область,
бренд, сервер или готовую структуру экранов. Его следует читать до проектирования
нового приложения, а затем адаптировать к доменной модели конкретного продукта.

Это не замороженный чеклист и не попытка заранее угадать идеальный интерфейс.
Стандарт задаёт устойчивый каркас, внутри которого продукт может меняться после
прототипов, пользовательских проб, аналитики и новых вводных без разрушения
базовых гарантий качества.

Для нового проекта команда должна:

1. Выделить основные пользовательские объекты и сценарии.
2. Составить матрицу прямых и обратных действий.
3. Определить правила и ограничения до реализации интерфейса.
4. Выбрать основной мобильный сценарий.
5. Применить требования из этого документа к каждому экрану и действию.
6. Сформулировать проверяемые критерии приёмки.
7. Проверить критические сценарии на реальном устройстве.

### 1.1 Четыре слоя стандарта

Каждое требование при переносе в новый продукт получает один из статусов:

| Слой | Что означает | Можно ли менять |
|---|---|---|
| `CORE` | Гарантия безопасности и управляемости продукта | Только с явным архитектурным решением |
| `DEFAULT` | Проверенный подход, подходящий большинству продуктов | Да, если есть причина и критерий проверки |
| `PROFILE` | Настройка конкретного продукта, аудитории или платформы | Да, это основной слой адаптации |
| `EXPERIMENT` | Временная гипотеза для пользовательской пробы | Да, должна иметь срок и решение по итогам |

Примеры `CORE`:

- пользовательские данные не теряются молча;
- разрушительное действие имеет защиту или восстановление;
- сервер не принимает недопустимое состояние;
- ошибка объясняет состояние результата;
- критическое действие доступно без hover;
- автоматический результат можно проверить и исправить.

Примеры `DEFAULT`:

- явная ручка для drag на прокручиваемой мобильной поверхности;
- undo toast после обычной мутации;
- основной рабочий сценарий на первом экране;
- touch target около 44×44 CSS px.

Примеры `PROFILE`:

- главная единица работы;
- порядок экранов;
- поддерживаемые платформы;
- допустимые варианты ответа;
- длительность сессии;
- тон сообщений;
- правила прогресса и напоминаний.

Примеры `EXPERIMENT`:

- новый способ онбординга;
- альтернативная механика повторения;
- другая навигация;
- AI-подсказка в конкретной точке;
- новый формат обратной связи;
- изменение плотности или порядка контента.

Новый продукт не копирует все `DEFAULT` автоматически. Команда сначала создаёт
`PROFILE`, отмечает неприменимые требования и формулирует эксперименты.

### 1.2 Профиль конкретного продукта

В новом репозитории рядом с этим стандартом создаётся короткий файл
`PRODUCT_USABILITY_PROFILE.md`. Он отвечает минимум на следующие вопросы:

```markdown
# Product Usability Profile

## Аудитория и контекст
- Кто основной пользователь?
- Где и на каком устройстве он работает?
- Как часто возвращается?
- Какие ограничения среды важны?

## Основная ценность
- Какое действие даёт первую ценность?
- Что пользователь должен продолжить при следующем открытии?
- Что считается завершённой сессией?

## Доменные объекты
- Основные сущности и их состояния.
- Какие данные создаёт пользователь, система и AI.

## Прямые и обратные действия
- Ссылка на доменную action/reverse matrix.

## Продуктовые правила
- Валидации, ограничения и configurable values.

## Платформы
- Mobile web / PWA / native / desktop / embedded WebView.

## Текущие эксперименты
- Гипотеза, аудитория, критерий успеха, срок, rollback.

## Осознанные отклонения от стандарта
- Требование, причина, риск, способ проверки.
```

Универсальный файл хранит принципы и процесс. `PRODUCT_USABILITY_PROFILE.md`
хранит изменяемые решения конкретного продукта. Нельзя записывать продуктовые
цифры, сущности и временные гипотезы в `CORE`.

### 1.3 Правило гибкости

Каркас должен позволять менять пользовательский сценарий без переписывания всего
продукта. Для этого:

- правила выносятся в конфигурацию или доменный слой, а не размазываются по UI;
- компоненты не содержат скрытых продуктовых ограничений;
- прямые действия оформляются как явные команды;
- обратные действия и migrations проектируются вместе с изменением;
- экспериментальные функции изолируются feature flag или чёткой границей;
- события аналитики имеют стабильные имена и версию схемы;
- пользовательские данные переживают смену интерфейса;
- устаревшие значения мигрируются, а не интерпретируются молча по новым правилам;
- документация различает действующее правило, гипотезу и наблюдение.

## 2. Базовые принципы

### 2.1 Любое изменение должно быть исправимым

Если пользователь может изменить состояние продукта, заранее должен существовать
понятный способ:

- отменить действие;
- восстановить удалённое;
- изменить автоматически выбранное значение;
- повторить сборку или настройку;
- вернуться к предыдущему состоянию;
- безопасно начать заново.

Функция не считается законченной, пока реализован только прямой путь.

### 2.2 Автоматизация предлагает, пользователь решает

Автоматически распознанные, сгенерированные или расставленные данные должны:

- оставаться редактируемыми;
- показывать, что именно поняла система;
- не уничтожать исходный ввод;
- позволять принять результат частично;
- объяснять, почему часть данных не обработана;
- иметь путь повторной обработки после исправления.

Автоматизация не должна превращать предположение системы в необратимое решение.

### 2.3 Предложение интерфейса является обещанием

Если интерфейс показывает, что действие возможно, сервер должен быть способен его
принять при тех же условиях. Нельзя:

- показывать доступный вариант, который затем отклоняется;
- подсвечивать место как подходящее, проверив только часть правил;
- разрешать preview, который нельзя сохранить;
- использовать разные ограничения в разных способах выполнения одного действия.

Логика подсказок должна проверять реальную выполнимость результата, а не только
грубое совпадение по размеру, длительности или категории.

### 2.4 Мобильный интерфейс является отдельной средой

Мобильная версия не должна быть уменьшенной копией desktop-интерфейса. Для неё
нужно отдельно определить:

- главный экран;
- порядок информации;
- размеры целей касания;
- поведение скролла и жестов;
- способ редактирования;
- доступность действий без hover;
- работу клавиатуры;
- safe areas и системные панели;
- standalone/PWA-сценарий, если он нужен продукту.

### 2.5 Правила продукта должны быть едиными

Одинаковые ограничения должны применяться в:

- форме создания;
- форме редактирования;
- быстром добавлении;
- drag-and-drop;
- автоматической обработке;
- пакетных операциях;
- клиентской валидации;
- серверной валидации.

Сервер является окончательным источником истины. Клиент обязан давать быструю и
понятную обратную связь, но не может иметь более свободные правила.

### 2.6 Ошибка пользователя не должна превращаться в тупик

После ошибки интерфейс должен сообщать:

- что произошло;
- что сохранилось;
- что не применилось;
- как исправить ситуацию;
- можно ли повторить действие.

Сообщение без следующего шага недостаточно полезно.

## 3. Этапы проектирования usability

### Этап 1. Определить реальные пользовательские задачи

Зафиксировать не экраны, а намерения пользователя. Например:

- начать или продолжить работу;
- создать объект;
- изменить объект;
- удалить объект;
- выполнить основную единицу работы;
- исправить ошибку;
- увидеть прогресс;
- изменить настройки;
- вернуться после перерыва.

Результат этапа: список задач в терминах пользователя.

### Этап 2. Определить доменные объекты и состояния

Для каждого объекта указать:

- обязательные поля;
- редактируемые поля;
- состояния жизненного цикла;
- связи с другими объектами;
- ограничения;
- источник создания: пользователь, система, импорт или автоматизация;
- что считается завершением;
- что должно сохраняться для восстановления.

Результат этапа: минимальная модель данных, достаточная для прямых и обратных
действий.

### Этап 3. Составить матрицу действий

До реализации для каждого изменения заполнить:

| Прямое действие | Обратное действие | Что сохраняется | Область отката |
|---|---|---|---|
| Создать объект | Удалить созданный | ID объекта | Один объект |
| Изменить объект | Вернуть прежние поля | Snapshot до изменения | Один объект |
| Удалить объект | Восстановить объект | Полный snapshot | Один объект и связи |
| Переместить/переупорядочить | Вернуть позицию | Прежний порядок | Коллекция |
| Пакетно изменить | Отменить пакет | Snapshot набора | Весь пакет |
| Автоматически обработать | Вернуть исходник | Исходный ввод и результат | Обработанная группа |
| Изменить настройки | Вернуть настройки | Предыдущая конфигурация | Пользователь/пространство |
| Сбросить прогресс | Восстановить или подтвердить | Backup/revision | Весь прогресс |

Результат этапа: ни одна мутация не остаётся без стратегии восстановления.

### Этап 4. Спроектировать основной мобильный путь

Нужно определить кратчайший путь от открытия приложения до основной ценности:

1. Что пользователь видит первым?
2. Как продолжает незавершённую работу?
3. Как начинает новую единицу работы?
4. Как исправляет результат?
5. Как понимает, что действие сохранено?
6. Как возвращается завтра?
7. Как продукт попадает на устройство пользователя и обновляется — с учётом бюджета,
   аккаунтов платформы и того, есть ли у команды физический доступ к устройству?

Ответ на седьмой вопрос выбирает платформу, а не наоборот: канал установки проверяется
до реализации, иначе готовый продукт может оказаться недоставляемым.

Первый экран должен быть рабочей поверхностью или точкой продолжения, а не
маркетинговой страницей и не обязательным объясняющим попапом.

### Этап 5. Спроектировать состояния и сбои

Для каждого экрана предусмотреть:

- initial;
- loading;
- empty;
- partially complete;
- success;
- validation error;
- network error;
- permission/auth error;
- stale data;
- offline, если продукт обещает offline;
- recovery after reload.

### Этап 6. Проверить на реальном устройстве

Эмуляция viewport необходима, но недостаточна. На целевом телефоне проверяются:

- касания пальцем;
- экранная клавиатура;
- safe areas;
- нативный overscroll;
- браузерные и встроенные WebView;
- PWA/standalone;
- медленная сеть;
- сворачивание и возвращение;
- потеря focus/pointer capture;
- изменение ориентации, если оно поддерживается.

### Этап 7. Провести пользовательскую пробу и обновить профиль

После технической проверки продукт показывается небольшой релевантной группе.
Цель пробы — не получить общее мнение «нравится / не нравится», а увидеть:

- где пользователь останавливается;
- что пытается нажать;
- какой смысл приписывает элементам;
- что делает не в предусмотренном порядке;
- где боится потерять результат;
- что исправляет вручную;
- какой обходной путь придумывает;
- что ожидает увидеть при возвращении.

После пробы команда:

1. Отделяет наблюдение от интерпретации.
2. Группирует повторяющиеся затруднения.
3. Проверяет, является ли проблема локальной или системной.
4. Формулирует гипотезу изменения.
5. Задаёт критерий успеха до реализации.
6. Выпускает минимально достаточный прототип.
7. Сравнивает результат с исходным поведением.
8. Принимает решение: принять, изменить, повторить или удалить.
9. Обновляет профиль продукта и только при необходимости универсальный стандарт.

## 3.1 Непрерывный цикл развития

После первого релиза этапы не заканчиваются. Продукт работает по циклу:

```text
Наблюдение
  → проблема
  → гипотеза
  → критерий успеха
  → минимальный прототип
  → пользовательская проба
  → данные и обратная связь
  → решение
  → rollout или rollback
  → обновление профиля и памяти продукта
```

Один отзыв является сигналом для проверки, но не автоматически универсальным
правилом. Один критический сбой безопасности или потеря данных может быть
достаточным основанием для немедленного исправления.

### Что обновляется после каждого цикла

- `PRODUCT_USABILITY_PROFILE.md` — действующие решения продукта;
- `EXPERIMENTS.md` — активные и завершённые гипотезы;
- `USABILITY_OBSERVATIONS.md` — фактические наблюдения пользователей;
- action/reverse matrix — новые или изменённые мутации;
- критерии приёмки и тесты;
- changelog — пользовательское изменение;
- этот универсальный стандарт — только подтверждённый переносимый принцип.

## 4. Универсальная матрица прямых и обратных действий

Ниже приведён базовый набор. В новом продукте он адаптируется к домену.

| Область | Прямое действие | Обратное или корректирующее действие |
|---|---|---|
| Навигация | Открыть другой раздел | Назад / возврат к предыдущему контексту |
| Создание | Создать запись | Удалить или отменить создание |
| Редактирование | Изменить поля | Вернуть предыдущие значения |
| Удаление | Удалить запись | Восстановить из snapshot/корзины |
| Порядок | Переместить элемент | Вернуть прежнюю позицию |
| Порядок | Поменять элементы местами | Повторный обмен / undo |
| Статус | Отметить завершённым | Снять отметку |
| Выбор | Выбрать вариант | Изменить или очистить выбор |
| Число | Ввести значение | Полностью очистить и ввести заново |
| Пакет | Применить ко многим | Отменить весь пакет или выбранную часть |
| Мастер | Завершить мастер | Открыть заново / пересобрать результат |
| Автоматизация | Принять предложение | Отредактировать / отклонить / повторить |
| Импорт | Импортировать данные | Удалить импортированный пакет |
| Настройки | Изменить правило | Вернуть предыдущее правило |
| Прогресс | Начать процесс | Выйти с сохранением / продолжить позже |
| Прогресс | Сбросить процесс | Подтвердить и сохранить возможность восстановления |
| Уведомления | Включить | Выключить и изменить частоту |
| Разрешения | Разрешить доступ | Отозвать / продолжить с ограниченной функцией |

Для каждого нового действия нужно ответить:

1. Какие сущности меняются?
2. Какие правила могут отклонить изменение?
3. Что нужно сохранить до изменения?
4. Как выглядит точная обратная команда?
5. Операция атомарная или пакетная?
6. Что произойдёт при частичном сбое?
7. Переживает ли undo перезагрузку?
8. Что видит пользователь после успеха и ошибки?

## 5. Архитектура отмены и восстановления

### 5.1 Простые действия

Для одиночной мутации достаточно хранить:

- тип действия;
- ID объекта;
- snapshot до изменения;
- ID созданного объекта, если объект новый;
- сообщение для пользователя;
- обратную команду;
- время жизни undo, если оно ограничено.

### 5.2 Пакетные действия

Пакетная операция должна хранить:

- ID всех созданных объектов;
- snapshots изменённых и удалённых объектов;
- прежний порядок;
- исходные пользовательские данные;
- статус каждого поддействия;
- безопасный порядок восстановления.

Если операция может завершиться частично, интерфейс не должен сообщать общий
успех. Он должен показать, что применилось, что не применилось и почему.

### 5.3 Операции с недопустимым промежуточным состоянием

Если два последовательных запроса временно нарушают правила, действие должно
быть отдельной атомарной серверной командой или транзакцией.

Примеры:

- обмен двух позиций;
- массовая замена связей;
- перенос прогресса между наборами;
- пересчёт зависимых результатов;
- удаление родителя с восстановлением дочерних объектов.

### 5.4 Разрушительные действия

Для действий, которые нельзя надёжно отменить:

- использовать явное подтверждение;
- конкретно назвать последствия;
- не ставить подтверждение на каждую обычную операцию;
- по возможности применять soft delete или версии;
- предложить экспорт/backup перед массовым сбросом.

## 6. Мобильные жесты и касания

### 6.1 У каждого жеста должна быть одна роль

Нельзя заставлять одну поверхность одновременно угадывать, хотел ли пользователь:

- прокрутить;
- открыть;
- перетащить;
- выделить текст;
- изменить размер.

Рекомендуемое разделение:

- тело элемента: обычный скролл и tap/open;
- явная ручка: drag;
- отдельная заметная зона: resize, если он действительно нужен;
- кнопка или меню: дополнительные команды.

### 6.2 Цели касания

Интерактивная зона должна быть рассчитана на палец, а не только на размер иконки.
Практический ориентир для важного мобильного действия: около 44×44 CSS px.

Проверяется не только визуальный размер, но и реальная hit area.

### 6.3 Никаких обязательных hover-состояний

Критические действия должны быть:

- видимыми постоянно;
- доступны через tap;
- представлены знакомой иконкой или ясной подписью;
- иметь accessible name;
- не зависеть от наведения курсора.

### 6.4 Жизненный цикл drag

Состояние drag должно очищаться на:

- `pointerup`;
- `touchend`;
- `pointercancel`;
- `touchcancel`;
- потерю pointer capture;
- `blur`;
- `visibilitychange`;
- unmount экрана.

Очищаются:

- preview;
- overlay;
- active pointer;
- auto-scroll;
- временная подсветка;
- классы блокировки скролла;
- listeners.

### 6.5 Скролл во время drag

На iOS и во встроенных WebView одних CSS-свойств может быть недостаточно.
Если drag начинается из явной ручки:

- `touch-action` задаётся по роли поверхности;
- прокручиваемая область использует containment;
- на время активного drag допустим non-passive `touchmove` с `preventDefault`;
- listener снимается на всех путях завершения;
- программный автоскролл целевого контейнера остаётся доступным;
- полный экран не должен растягиваться или закрывать приложение.

### 6.6 Автоскролл

Автоскролл должен работать во всех поверхностях, где разрешено перемещение, а не
только в одной реализации вида. Проверяются верхний и нижний края, пределы
контейнера и завершение автоскролла после отмены жеста.

### 6.7 Альтернатива жесту

Drag не может быть единственным способом точного изменения. Нужен доступный
альтернативный путь через редактор, меню или кнопки. Это важно для:

- моторных ограничений;
- screen reader;
- сложных мобильных WebView;
- точного изменения значения;
- восстановления после неудачного жеста.

## 7. Формы и ввод

### 7.1 Числовое поле должно позволять пустое состояние

Пользователь должен иметь возможность стереть значение целиком и ввести новое.
Нельзя на каждом `onChange` немедленно заменять пустую строку значением по
умолчанию.

Правильная модель:

- во время редактирования хранить строку;
- разрешать `""`;
- проверять число при подтверждении или blur;
- показывать ограничение рядом с полем;
- не терять введённое при ошибке.

### 7.2 Пресет не является фиксированным значением

Быстрый вариант должен ускорять ввод, но не блокировать редактирование.

Например, выбор условного «полного режима» может поставить значение по умолчанию,
после чего пользователь должен иметь возможность изменить длительность, объём,
уровень или состав результата.

### 7.3 Значения по умолчанию

Default допустим, если он:

- честно отображён;
- подходит большинству сценариев;
- легко меняется;
- не возвращается сам после очистки;
- не маскирует отсутствие обязательного выбора.

### 7.4 Экранная клавиатура

На телефоне проверяются:

- правильный `inputmode`;
- возможность удалить первый и последний символ;
- доступность кнопки сохранения над клавиатурой;
- отсутствие перекрытия активного поля;
- переход между полями;
- поведение Enter/Done;
- сохранение черновика при закрытии клавиатуры.

### 7.5 Редактор должен показывать все изменяемые свойства

Если объект можно изменить жестом или автоматизацией, соответствующие поля должны
быть доступны в обычном редакторе. Пользователь не должен повторять сложный жест,
чтобы исправить точное значение.

## 8. Автоматический разбор, AI и предложения

### 8.1 Сохранять оригинал

Любой parser или AI-преобразователь должен хранить исходный ввод до принятия
результата. Пользователь должен видеть связь между оригиналом и структурированным
результатом.

### 8.2 Возвращать частичный результат

Система не должна падать из-за одного нераспознанного поля. Возможные результаты:

- распознано полностью;
- распознано частично;
- неоднозначно;
- конфликтует с правилом;
- не распознано.

Для каждого состояния нужен понятный следующий шаг.

### 8.3 Приоритет явного над неявным

Более точный пользовательский ввод должен иметь приоритет над пресетом или
догадкой системы. Порядок правил фиксируется и покрывается тестами.

### 8.4 Не удалять необработанное

При пакетной обработке успешно обработанные элементы могут перейти дальше, а
остальные должны сохраниться с причиной. Нельзя очищать весь список после
частичного успеха.

### 8.5 Результат остаётся редактируемым

После автоматизации пользователь может:

- изменить поля;
- удалить результат;
- вернуть исходник;
- повторить обработку;
- применить другой вариант;
- отменить весь пакет.

### 8.6 Проверять фактическую выполнимость

Предложение должно проходить те же доменные правила, что и сохранение. Если
подходящий результат существует только при дополнительном условии, интерфейс
либо автоматически соблюдает его, либо явно сообщает условие до действия.

### 8.7 Внешний источник данных, который ведёт человек

Статус: `DEFAULT` (кандидат — подтверждён одним продуктом, см. changelog 1.4).

Если данные продукта ведёт человек в своём рабочем инструменте (таблица, папка
файлов, документ), а продукт их импортирует или синхронизирует:

- процесс автора сохраняется: продукт подстраивается под формат источника и не
  требует от автора служебных форматов (JSON, идентификаторы, жёсткие шаблоны);
- поля находятся по смыслу заголовков, а не по фиксированным позициям; пустые
  ячейки-продолжения (раздел указан только в первой строке группы) разбираются
  так, как их читает человек;
- перечни, которые растут вместе с контентом (категории, разделы, группы),
  строятся из данных, а не зашиваются в код — даже если в ТЗ перечислен
  фиксированный набор;
- связь записей с файлами устанавливается только по однозначным правилам;
  нечёткое совпадение показывается автору как подсказка и не применяется молча;
- явная ссылка автора (имя файла, ссылка) имеет приоритет над автоматическим
  сопоставлением;
- несопоставленное не блокирует остальное: запись работает частично, а автор
  получает отчёт — место (строка, поле), причина и следующий шаг;
- отчёт доступен автору без разработчика (экран в продукте или файл);
- сбой загрузки источника не уничтожает последнюю рабочую версию данных;
- до реализации интерфейса сопоставление прогоняется на реальной выгрузке
  данных, а расхождения с ТЗ фиксируются явно.

## 9. Навигация и раскрытие сложности

### 9.1 Основной сценарий на первом экране

После открытия пользователь должен быстро понять:

- где он находится;
- что уже сделано;
- что делать дальше;
- как продолжить незавершённое;
- где исправить результат.

Не следует показывать обязательный стартовый попап при каждом открытии. Обучение
лучше давать контекстно в момент первого релевантного действия.

### 9.2 Несколько представлений

Разные виды допустимы, если у них различаются задачи. Для каждого вида нужно
проверить полный набор операций и состояний. Нельзя считать, что исправление в
одном представлении автоматически исправило остальные.

### 9.3 Возврат к текущему контексту

При навигации по периодам, разделам или уровням нужен простой путь:

- назад;
- к текущему состоянию;
- к последней незавершённой работе;
- к исходному списку после редактирования.

### 9.4 Многошаговый мастер

Мастер должен позволять:

- вернуться на предыдущий шаг;
- сохранить введённое;
- выйти без потери черновика;
- увидеть итог до применения;
- применить понятные элементы;
- оставить проблемные элементы для исправления;
- открыть мастер снова и пересобрать результат;
- отменить пакетный результат.

### 9.5 Интерактивные задания и сборка порядка

Для интерфейсов, где пользователь сопоставляет, классифицирует или меняет
порядок элементов, действуют следующие требования `DEFAULT`:

- начальное состояние не должно случайно показывать готовый правильный ответ;
- если порядок является частью задачи, исходный набор действительно перемешан и
  это проверяется отдельно от проверки итогового ответа;
- drag-and-drop дополняется кнопками или клавиатурным управлением, а не является
  единственным способом выполнить действие;
- до первого действия понятно, что выбрать сначала и что произойдёт дальше;
- выбранный элемент и текущий шаг визуально различимы;
- следующий классифицируемый или сопоставляемый элемент виден сразу после выбора;
- сделанную пару, категорию или порядок можно изменить до подтверждения;
- итог проверяется теми же правилами и в том же представлении, которое видит
  пользователь; канонически правильный результат нельзя отклонить из-за
  внутреннего формата, повторяющихся слов или служебных идентификаторов.

Для диалогов и других последовательностей каждая смысловая единица показывается
отдельной строкой. Участники, шаги или роли обозначаются явно; служебный контекст
не смешивается с пользовательским содержанием и не выглядит его частью.

## 10. Обратная связь, ошибки и тон

### 10.1 Успех

После мутации нужен короткий сигнал:

- что изменилось;
- сохранено ли изменение;
- доступно ли undo.

Нельзя использовать длительную анимацию, которая мешает следующему действию.

### 10.2 Ошибка

Хорошая ошибка содержит:

1. Объект или действие, которое не удалось.
2. Причину понятным языком.
3. Состояние данных после ошибки.
4. Следующий возможный шаг.

Плохие варианты:

- «Что-то пошло не так» без контекста;
- технический текст API;
- обвиняющая формулировка;
- исчезновение введённых данных;
- сообщение о запрете после того, как UI сам предложил действие.

Сообщение пользователю не должно содержать внутренние идентификаторы, обрезки
ключа, технические названия категорий или фрагменты данных без контекста. Для
составного ответа оно называет понятный элемент или действие: что пропущено,
какая связь неверна и что пользователь может сделать дальше.

Для заданий и форм с автоматической проверкой дополнительно обязательно:

- принимать естественные смысловые эквиваленты, если задача не требует точной цитаты;
- согласовать число обещанных действий, видимых полей, элементов ключа и частей эталона;
- не показывать внутренние имена вариантов, веток эксперимента и служебные суффиксы;
- проверять альтернативный естественный ответ отдельным регрессионным сценарием;
- до публикации автоматически сопоставлять инструкцию, поля, ключ, подсказки и аудио.

### 10.3 Подсказки

Подсказки должны быть:

- контекстными;
- короткими;
- исчезающими после освоения;
- не блокирующими основной интерфейс;
- согласованными с реальными правилами;
- не повторяющими очевидные элементы экрана.

### 10.4 Спокойный интерфейс прогресса

В продуктах регулярной практики интерфейс не должен усиливать чувство провала.
Следует различать:

- факт прогресса;
- мягкое напоминание;
- обязательное ограничение;
- рекомендацию;
- достижение.

Рекомендация не должна выглядеть как ошибка, а пропуск не должен уничтожать
ощущение накопленного прогресса.

## 11. Состояния, сохранение и надёжность

### 11.1 Optimistic UI

Оптимистическое обновление допустимо, если:

- есть rollback при ошибке API;
- пользователь понимает статус сохранения;
- повторный запрос идемпотентен или защищён ключом;
- локальное состояние сверяется с сервером после сбоя.

### 11.2 Перезагрузка и возврат

После reload, закрытия вкладки или возврата в приложение:

- завершённые изменения не пропадают;
- незавершённый важный ввод восстанавливается или явно сбрасывается;
- временные drag/preview-состояния не остаются;
- приложение открывает логичный контекст;
- повторяющиеся системные данные не дублируются.

### 11.3 Offline

Нельзя обещать offline только потому, что приложение устанавливается как PWA.
Для настоящего offline нужны:

- локальная модель данных;
- очередь мутаций;
- стратегия синхронизации;
- разрешение конфликтов;
- индикация статуса;
- тесты восстановления сети.

Без этого PWA является способом установки и standalone-запуска, а не offline-app.

## 12. Доступность

Минимальные требования:

- все кнопки имеют accessible name;
- видимый focus для клавиатуры;
- логичный порядок tab;
- достаточный контраст;
- состояние не кодируется только цветом;
- текст масштабируется без перекрытий;
- действия доступны без drag;
- важные сообщения объявляются assistive technology;
- формы связаны с label и ошибками;
- touch targets достаточно велики;
- reduced motion учитывается для необязательных анимаций.

## 13. PWA и standalone

Если продукт предполагает установку на телефон, нужны:

- HTTPS;
- manifest;
- название и short name;
- иконки платформенных размеров;
- `display: standalone`;
- theme/background colors;
- Apple metadata, если поддерживается iPhone;
- корректный viewport и safe areas;
- понятная инструкция установки;
- проверка запуска с домашнего экрана;
- проверка auth/cookies в standalone-контексте;
- отсутствие ложного обещания offline.

Установка должна улучшать основной сценарий, а не быть обязательной для доступа
к базовой функциональности.

### 13.1 Если продукт — нативное мобильное приложение

Статус: `DEFAULT`. Формулировки стандарта местами web-ориентированы (CSS px,
hover, reload, PWA). Для нативного приложения требования переносятся так:

| Требование стандарта | Нативный эквивалент |
|---|---|
| Touch target около 44×44 CSS px | Около 44×44 pt (iOS) / 48×48 dp (Android) у реальной зоны касания |
| Текст масштабируется без перекрытий | Системные текстовые стили и масштаб шрифта ОС (Dynamic Type / font scale), крупные цифры — с масштабированием |
| Accessible name | Метки и подсказки для экранного диктора, признаки «заголовок», «выбрано» |
| Reduced motion | Системная настройка уменьшения движения |
| Нет обязательного hover | Hover отсутствует; все действия видимы и доступны касанием |
| Reload и возврат (11.2) | ОС может выгрузить приложение в фоне: незавершённая работа сохраняется на диск после каждого действия, при запуске первый экран предлагает продолжить |
| Offline (11.3) | Локальный кэш и очередь загрузок с докачкой; статус «нет сети» виден, но не выглядит ошибкой, если работа возможна |
| Разрешения (матрица §4) | Системный запрос — в момент первого релевантного действия, а не при запуске; после отказа — объяснение и путь в системные настройки |
| Несколько устройств одного пользователя | Синхронизация через аккаунт платформы; дубли после офлайн-правок на двух устройствах схлопываются, у настроек устройства (например, уведомлений) есть локальный переключатель |
| Время и таймеры | Отсчёт от момента окончания, а не по тикам: таймер переживает сворачивание; о завершении в фоне сообщает локальное уведомление |
| PWA и standalone (§13) | Не применяется; вместо этого выбирается канал установки (магазин, тестовая раздача, внутренняя установка) |
| Проверка на реальном устройстве (15.4) | Симулятор не заменяет устройство: уведомления, звук в беззвучном режиме, фон и синхронизация аккаунта проверяются только на устройстве |
| Канал установки (этап 4, вопрос 7) | Выясняется до выбора платформы. Пример ограничения: бесплатная подпись iOS требует подключать устройство к компьютеру разработчика и переподписывать раз в 7 дней; удалённая установка — только через платную программу разработчика. Без бюджета и без доступа к устройству остаётся веб-приложение |

## 14. Применение к приложению изучения языка

Этот раздел не задаёт продуктовые решения. Он показывает, какие вопросы нужно
закрыть при адаптации универсальных требований к language-learning продукту.
Все перечисленные ниже объекты и механики имеют статус `PROFILE` или
`EXPERIMENT`, пока их не подтвердят вводные и пользовательские пробы нового
продукта.

### 14.1 Возможные доменные объекты

Команда должна уточнить модель, но типовой набор может включать:

- язык и направление обучения;
- курс или учебный маршрут;
- модуль;
- урок;
- упражнение;
- попытку ответа;
- карточку слова/фразы;
- повторение;
- пользовательскую цель;
- прогресс;
- ошибку или сложный материал;
- напоминание;
- пользовательский словарь;
- настройки сложности и темпа.

### 14.2 Обязательные пары действий

| Прямое действие | Что нужно предусмотреть в обратную сторону |
|---|---|
| Выбрать язык/уровень | Изменить выбор без потери совместимого прогресса |
| Начать курс | Выйти, архивировать или начать другой |
| Начать урок | Поставить на паузу и продолжить с места остановки |
| Отправить ответ | Показать разбор; определить, можно ли изменить до проверки |
| Принять AI-проверку | Оспорить, исправить или отправить на повторную проверку |
| Добавить слово | Удалить или отредактировать карточку |
| Удалить слово | Восстановить карточку и историю повторений |
| Изменить порядок уроков | Вернуть рекомендованный или предыдущий порядок |
| Настроить цель | Изменить объём и расписание без наказания за прошлое |
| Пропустить задание | Вернуться к нему позже |
| Отметить материал знакомым | Вернуть в активное изучение |
| Сбросить прогресс | Подтвердить, экспортировать и по возможности восстановить |
| Импортировать словарь | Удалить конкретный импортированный пакет |
| Включить напоминания | Изменить частоту или отключить |

### 14.3 Особые usability-риски language learning

- Ошибочный ответ является частью обучения, а не системной ошибкой.
- AI-оценка произношения или текста не должна подаваться как абсолютная истина.
- Пользователю нужен разбор, а не только красный/зелёный результат.
- Прогресс должен переживать паузы и смену устройства.
- Streak не должен превращать пропуск дня в потерю всей мотивации.
- Уровень и темп должны изменяться без обязательного полного сброса.
- Аудио требует явных состояний записи, обработки, ошибки разрешения и повтора.
- Упражнение должно быть доступно без жестов, требующих высокой моторной точности.
- Автоматически созданные карточки должны редактироваться.
- Повторение должно объяснять, почему материал появился снова.
- Клавиатуры разных языков не должны ломать навигацию и проверку формы.
- Транслитерация, диакритика, регистр и допустимые варианты ответа должны быть
  частью формализованных правил, а не случайными исключениями в UI.

### 14.4 Вопросы до начала реализации

1. Что является основной единицей ценности: урок, практика, повторение или диалог?
2. Что пользователь должен увидеть при следующем открытии?
3. Какие ответы проверяются строго, а какие допускают варианты?
4. Где решение принимает правило, где AI, где преподаватель, где пользователь?
5. Как пользователь оспаривает или исправляет автоматическую оценку?
6. Что сохраняется внутри незавершённого упражнения?
7. Как меняется уровень без потери истории?
8. Как устроены повторения и можно ли управлять ими вручную?
9. Какие действия влияют на статистику и можно ли их отменить?
10. Какие сценарии обязаны работать на телефоне одной рукой?

## 15. Проверка качества

### 15.1 Функциональные проверки

- каждое прямое действие работает;
- каждое обратное действие восстанавливает ожидаемое состояние;
- undo работает после последовательности действий;
- batch undo не оставляет частичных данных;
- клиент и сервер применяют одинаковые правила;
- автоматизация сохраняет исходный ввод;
- частичный успех не удаляет проблемные элементы;
- повторный запрос не создаёт дубли;
- reload не возрождает удалённые системные элементы;
- настройки применяются ко всем путям выполнения действия.
- канонически правильный составной ответ принимается, в том числе при
  повторяющихся словах и одинаковых окончаниях элементов;
- задание на порядок стартует не в эталонном порядке;
- после каждого шага классификации или сопоставления виден следующий элемент;
- выбранная пара и порядок редактируются до подтверждения;
- переход в справку или форму обратной связи возвращает в исходный контекст без
  потери незавершённой работы.

### 15.2 Мобильные проверки

- основной сценарий проходит одной рукой;
- важные действия видимы без hover;
- touch targets подходят для пальца;
- обычный скролл не запускает drag;
- drag не тянет весь экран;
- автоскролл работает во всех нужных видах;
- отмена жеста очищает preview;
- клавиатура не закрывает поле и кнопку сохранения;
- числовое поле можно полностью очистить;
- длинный текст не выходит из контейнера;
- safe areas не перекрывают интерфейс;
- PWA запускается и сохраняет авторизацию;
- возврат после background не оставляет ложное активное состояние.

### 15.3 Состояния и ошибки

- loading не выглядит как пустой результат;
- empty state предлагает релевантное действие;
- ошибка сохраняет введённые данные;
- сообщение объясняет следующий шаг;
- offline не маскируется под успешное сохранение;
- optimistic UI откатывается после ошибки;
- частичный сбой отображается поэлементно;
- destructive action требует соразмерного подтверждения.

### 15.4 Проверка на реальном устройстве

Минимум один проход выполняется:

- на целевом iPhone/Safari;
- в standalone/PWA, если он поддерживается;
- во встроенном WebView, если ссылки могут открываться из мессенджера;
- при медленной или нестабильной сети;
- с экранной клавиатурой целевых языков;
- после сворачивания и возвращения;
- с увеличенным системным размером текста.

## 16. Антипаттерны

Не допускаются:

- прямое действие без обратного пути;
- пустое числовое поле, мгновенно превращающееся в прежнюю цифру;
- drag с тела прокручиваемого элемента;
- важная кнопка, видимая только по hover;
- подсказка, обещающая недопустимый результат;
- разные правила для quick-add, editor и API;
- очистка всего списка после частичного успеха;
- потеря исходного текста после автоматического разбора;
- автоматический результат, который нельзя отредактировать;
- обязательный стартовый попап при каждом запуске;
- сообщение об ошибке без способа исправления;
- пустой экран после сбоя интерфейса — вместо него объяснение, что сохранено, и путь
  перезапуска;
- сообщение с внутренним идентификатором или фрагментом ключа вместо понятного
  пользовательского объяснения;
- задача на порядок, которая при открытии уже показывает правильный порядок;
- drag-and-drop без доступной альтернативы кнопками или клавиатурой;
- сопоставление, где пользователь не понимает, что выбрать первым или где
  появится следующий элемент;
- диалог, собранный в одну строку без различимых участников и реплик;
- справка или обратная связь, из которой нельзя вернуться к исходной работе;
- PWA, объявленная offline-приложением без синхронизации;
- исправление только одного из нескольких мобильных представлений;
- desktop-проверка вместо теста на реальном телефоне;
- прогресс, который необратимо уничтожается из-за изменения настройки;
- мотивационная механика, наказывающая пользователя за нормальный перерыв.

## 17. Definition of Done для usability

Функция готова только если:

- пользовательское намерение сформулировано;
- прямое и обратное действия определены;
- данные для восстановления сохраняются;
- правила одинаковы на клиенте и сервере;
- предусмотрены loading/empty/error/success states;
- автоматический результат редактируется;
- мобильный путь не зависит от hover;
- есть альтернатива сложному жесту;
- touch targets и клавиатура проверены;
- ошибки сохраняют контекст и дают следующий шаг;
- lint/typecheck/build/tests проходят;
- критический путь проверен на реальном устройстве;
- для экспериментальной функции есть flag/rollback и критерий решения;
- наблюдения отделены от продуктовых выводов;
- профиль продукта обновлён после принятого изменения;
- пользовательская документация и changelog обновлены.

## 18. Инструкция будущему агенту

При разработке нового продукта агент должен:

1. Прочитать этот документ до проектирования интерфейса.
2. Изучить вводные и существующий код нового проекта.
3. Не переносить конкретные сущности или правила из предыдущих продуктов.
4. Составить доменную матрицу прямых и обратных действий.
5. Выделить основной мобильный сценарий.
6. Проверить формы, жесты, автоматизацию и состояния по соответствующим разделам.
7. Формализовать критерии приёмки до реализации.
8. Реализовать и проверить прямой и обратный путь вместе.
9. Зафиксировать новые usability-уроки в этом стандарте только в универсальной форме.

Агент не должен превращать первый отзыв пользователя в постоянное общее правило.
Он должен сначала классифицировать входящий сигнал:

- `BUG` — поведение противоречит уже принятому правилу;
- `FRICTION` — пользователь достигает цели, но с лишними усилиями;
- `MISUNDERSTANDING` — интерфейс и пользовательская модель расходятся;
- `REQUEST` — новая желаемая возможность;
- `HYPOTHESIS` — возможное улучшение без достаточных данных;
- `CONSTRAINT` — новая обязательная вводная среды или бизнеса.

Затем агент выбирает минимальный способ проверки и сохраняет возможность
rollback. Только повторяемое наблюдение или сильное доказательство переводит
локальный урок в reusable-стандарт.

Если требование документа не применимо к конкретному продукту, агент должен не
молча пропустить его, а кратко зафиксировать причину в техническом решении.

## 19. Управление экспериментами

### 19.1 Карточка эксперимента

Каждая пользовательская проба фиксируется до реализации:

```markdown
# Experiment: <короткое название>

- Статус: planned | running | accepted | revised | rejected
- Слой: EXPERIMENT
- Наблюдение: что произошло без интерпретации
- Проблема: какое пользовательское намерение затруднено
- Гипотеза: если изменить X, то Y улучшится, потому что Z
- Аудитория: для кого проверяем
- Вариант/прототип: минимальное изменение
- Baseline: как выглядит исходное поведение
- Критерий успеха: измеримый или наблюдаемый сигнал
- Guardrails: что не должно ухудшиться
- Срок/объём пробы: когда принимается решение
- Rollback: как безопасно выключить изменение
- Результат: данные и наблюдения
- Решение: принять | изменить | повторить | удалить
- Изменённые документы и тесты: ссылки
```

### 19.2 Критерии хорошего эксперимента

- проверяет одну основную гипотезу;
- не требует полной перестройки до получения сигнала;
- не подвергает риску пользовательские данные;
- имеет baseline;
- имеет критерий остановки;
- может быть выключен;
- не меняет скрытно смысл уже сохранённых данных;
- собирает минимум данных, достаточный для решения;
- не выдаёт эксперимент за обещанную постоянную функцию.

### 19.3 Решение после эксперимента

Возможны четыре результата:

- `ACCEPT` — гипотеза подтверждена, решение становится частью `PROFILE`;
- `REVISE` — проблема подтверждена, конкретное решение требует новой итерации;
- `REPEAT` — данных недостаточно или выборка нерелевантна;
- `REJECT` — решение не улучшило сценарий и удаляется.

Эксперимент становится `DEFAULT` универсального стандарта только если:

- паттерн повторился в разных пользователях или продуктах;
- причина понятна, а не только коррелирует с результатом;
- известны границы применимости;
- решение не создаёт большего ущерба в другом сценарии;
- есть воспроизводимый критерий проверки.

## 20. Журнал пользовательских наблюдений

Наблюдение записывается отдельно от решения:

```markdown
## Observation <date/id>

- Контекст и устройство:
- Задача пользователя:
- Что пользователь сделал:
- Где остановился или ошибся:
- Что сказал дословно:
- Как восстановился:
- Частота: один случай | повторяется
- Severity: блокирует | затрудняет | косметика
- Связанный сценарий/событие аналитики:
- Возможные гипотезы (не решения):
```

Не следует записывать «пользователю нужна кнопка» как наблюдение. Наблюдение —
«пользователь трижды пытался нажать на заголовок, чтобы вернуться». Кнопка — одна
из гипотез решения.

## 21. Архитектурная готовность к изменениям

Гибкость интерфейса невозможна без гибкости реализации. Для активно развиваемого
продукта рекомендуются:

- конфигурационный слой для изменяемых правил;
- schema/version для настроек и событий;
- migrations для сохранённых данных;
- feature flags для рискованных или альтернативных сценариев;
- стабильные доменные команды вместо мутаций из UI-компонентов;
- централизованная валидация;
- idempotency для повторяемых запросов;
- audit/event log там, где важна история;
- analytics events, связанные с пользовательским намерением;
- возможность сегментировать результаты пробы без сбора лишних данных;
- компоненты с явными контрактами состояний;
- удаление завершённых flags и старых веток после принятия решения.

Нельзя строить абстракцию «на все будущие случаи». Готовность к изменениям — это
ясные границы, конфигурация реально изменяемых правил, обратимые команды и дешёвый
цикл проверки, а не максимальная универсальность кода заранее.

### Изменения версии 1.2

- Основание: пользовательское прохождение многошаговых учебных интерфейсов
  выявило повторяемые классы ошибок — готовый порядок на старте, ложное
  отклонение правильного результата, неясный следующий шаг, тупик после справки
  и смешение служебного контекста с содержанием.
- Добавлены универсальные требования к ORDER/MATCH/CLASSIFY-подобным механикам,
  диалогам, тексту ошибок и возврату в исходный контекст.
- Уточнены функциональные проверки и антипаттерны для новых проектов.

При изменении этого файла:

1. Повышается версия в начале документа.
2. В changelog фиксируется причина, а не только текст правки.
3. Указывается, какой пользовательский сигнал или продуктовый опыт стал основанием.
4. Неактуальное правило помечается deprecated до удаления, если на него могут
   ссылаться действующие профили.
5. `CORE` меняется только с описанием риска и миграции.
6. `DEFAULT` может быть уточнён после подтверждённых проб.
7. Продуктовые значения остаются в `PROFILE`, а не переносятся в стандарт.
8. Копии стандарта синхронизируются с reusable-ресурсом Second Brain.
